# Agent guidance

Casey Gollan's personal website uses SvelteKit 2, Svelte 5, TypeScript, Vite, and Bun. Production is a Cloudflare Worker with static assets, not Pages. Use the existing Wrangler configuration and pinned dependencies.

## Commands

- `bun install`: install dependencies.
- `bun run dev`: fast Vite development; no Cloudflare bindings.
- `bun test`: regression tests.
- `bun run check`: Svelte/TypeScript diagnostics. Existing errors remain; record the baseline and report new failures separately.
- `bun run build`: initialize the content submodule, then build with Vite.
- `bun run preview`: build and start Wrangler with local KV/R2 bindings.
- `bun run preview:remote`: build and connect to remote bindings; use only when remote resource access is intended.
- `bun run deploy`: build and change production. For packaging checks, use `bun run wrangler deploy --dry-run` instead.
- `bun run update-library`: process the LibraryThing export into library data and covers.

Use Bun for package management and local scripts. Run tests and a production build for code changes. Check the homepage and library after visualization changes, and posts/tag/date routes after content changes.

## Architecture

- `src/routes/+page.svelte`: interactive bio and homepage.
- `src/lib/components/SkillsGraph.svelte`: D3 skills visualization.
- `src/routes/library/[[isbn]]/`: Three.js book graph and detail view.
- `src/app.css`: design tokens (color, type scale, space, radius, motion) and global base styles. Use tokens instead of literal values.
- `src/lib/components/ui/`: presentational primitives (`Page`, `PageHeader`, `Heading`, `Button`, `Icon`, `Chip`, `ToggleChip`, `SegmentedPill`, `SelectMenu`, `Popover`, `Disclosure` (a summary that opens, nestable), `JsonView`, `SidePanel` (the panel under the navigation that the library's book details and the docked chat share), `FloatingButton` (the round corner buttons: sound, chat), `ChoiceMenu` (a round button that opens a menu of a few choices, one in effect), `CommandPalette`, `TextField`, `Checkbox`, `CheckboxGroup`, `Switch`, `Notice`, `Section`, `Tabs` (settings groups: a list beside its panels where there is room, a row above them otherwise), `RowList`/`Row` (one line and at most one action each), `Prose`, ...). Interactive ones are built on ui-sdk. See "UI work" below.
- `/account` and `src/lib/components/account/` (Storybook `Site/Account`): the owner's settings. Signed in, the page is `Tabs` of groups (Tools, Skills, Connections, Newsletter, Security); the open group is the address's hash (`/account#connections`), and `ANCHORS` in the route maps ids inside a group, where sign-in callbacks land (`#bluesky`, `#connections-chat`), to it. A new service goes in the Connections group as its own self-contained component, not a new group. An app's IndieAuth request (`?request=`) and signing in each get the page to themselves (`ConsentRequest`, `AccountSignIn`), with no settings around them.
- `src/lib/components/posts/`: post components built from the primitives; routes render feeds with `PostFeed`.
- `.storybook/` and `*.stories.{ts,svelte}`: Storybook, published at `/storybook/`. Add a story for each new component; `Foundations/Tokens` documents the tokens.
- `src/lib/posts.ts`: Vite-bundled Markdown snapshot; shared parsing is limited to production builds.
- `src/lib/server/`: shared Markdown parser and server-side content helpers.
- `src/lib/utils/htmlToMarkdown.ts`: posts are stored as Markdown by default. Imported (PESOS) and edited HTML is converted when `sameRendering` confirms the Markdown renders identically; otherwise it stays HTML. `utils/convert-html-content.ts` applies the same rule to the content repository.
- `src/lib/components/composer/` and `src/lib/components/editor/`: shared composer parts (`ComposerBar`, `ComposerToolbar`, `FrontmatterProperties`, with `Button` and `Icon` from `ui/`) used by `/new` and the post editor. The rich editor (`MarkdownEditor`, Lexical) reads post figures (`<figure>` HTML, see `src/lib/markdown-figure.ts`) into `FigureNode` blocks drawn by `EditableFigure`, and writes untouched figures back byte for byte.
- Post slugs: the editor's `slug` property row (`FrontmatterProperties`) sends Micropub `mp-slug` on update, which moves the file in one commit (add + delete) and records the old path in `_micropubPreviousUrls`. The post, edit and syndicate routes redirect old paths from the bundled posts (`movedPost` in `src/lib/post-slug.ts`); a post living at an address wins over a redirect. Delivery treats a renamed post as the same publication: no removal for the old address, and syndication receipts under old addresses still count, so it is never posted again.
- Syndication threads: a post's `syndication-thread` (one value per post) and `syndication-photo-post` (parallel to `photo`) hold the social copy as a reply chain; Micropub accepts them and advertises them in `q=config`, automatic delivery and the syndicate page (`ThreadComposer`, "Save thread") use them, and every sent post's URL goes in `syndication`. They are not part of the publication revision, so editing a thread never resends. Proposal and spec diff: `docs/indieweb-publishing/proposals/micropub-syndication-threads.md`.
- Bluesky posting signs in with atproto OAuth (`src/lib/server/publishing/bluesky-oauth.ts`, `dpop.ts`): the Worker is a confidential client whose metadata is `/oauth/bluesky/client-metadata.json` (production origin only); the owner connects on `/account` (`BlueskySettings`, `/api/bluesky/oauth`), and `/oauth/bluesky/callback` finishes it. The client key, DPoP key and tokens live in `PUBLISHING_STATE` under `private/bluesky-oauth/`; refreshes run one at a time under a lease. The scope is posts (create/update) and image uploads only. `blueskyAgent` uses OAuth when connected and falls back to the app password (`PUBLISHING_BLUESKY_PASSWORD`) when OAuth is missing or refused, noting why on `/account`; `PUBLISHING_BLUESKY_OAUTH=false` turns OAuth off.
- Mastodon posting signs in with the instance's own OAuth (`src/lib/server/publishing/mastodon-oauth.ts`), the counterpart of Bluesky's: the Worker registers itself as an app on `PUBLISHING_MASTODON_INSTANCE` once (`POST /api/v1/apps`, per instance and callback address), the owner connects on `/account` (`MastodonSettings`, `/api/mastodon/oauth`), and `/oauth/mastodon/callback` finishes it (authorization code with PKCE, a state bound to the browser by cookie). The app's client secret and the session live in `PUBLISHING_STATE` under `private/mastodon-oauth/`. The scope is posting, media uploads, and reading the account's own posts and favourites for the importer. Mastodon tokens don't expire, so there is no refresh. `mastodonCredentials` gives sends and PESOS the OAuth token when connected and the static token (`PUBLISHING_MASTODON_TOKEN`) otherwise; a send the instance refuses (401, 403) is retried with the static token under the same idempotency key, a 401 marks the connection for reconnecting, and `/account` shows why. `PUBLISHING_MASTODON_OAUTH=false` turns OAuth off. The instance address is checked with `publicUrl` and every request goes through `safePublicFetch`. `BlueskySettings` and `MastodonSettings` are both the shared `account/OAuthConnection`.
- `src/routes/wiki/` and `src/lib/wiki/`: the wiki browser for cag.wiki (Casey's Obsidian Publish vault). `utils/wiki-vault.ts` fetches every published page at build time; `utils/build.ts` fetches once, in parallel with the other steps, into `.svelte-kit/build-wiki/vault.json` (`WIKI_VAULT`), and both the search index and the Vite plugin (`utils/vite-wiki.ts`, modules `virtual:wiki-vault` and `virtual:wiki-manifest`) read it. `src/lib/wiki/build.ts` renders wikilinks, embeds, footnotes, backlinks and the graph. Components are in `src/lib/components/wiki/` (Storybook `Wiki/*`). `localizeLinks`/`wikiHref` in `src/lib/wiki/links.ts` point cag.wiki links anywhere on the site at `/wiki/<slug>`; `WikiPreviews`, mounted in the root layout, previews them on hover. On wide screens `WikiStack` opens wiki links as sliding panes beside the page, as cag.wiki does: the open panes live in `?stack=` (read client-side, since pages are prerendered) and in shallow-routing history, and each pane loads `/wiki/<slug>/page.json`. Wiki pages also render Dataview `key:: value` lines as details (`fields`), hide `%%` comments, and mark external links. The dev server and Storybook carry on with an empty wiki when offline; a site build fails instead.
- `src/routes/tables/` and `src/lib/components/tables/`: tables, tldraw canvases of blocks from site search (`src/lib/table-sources.ts`) and links. tldraw is React, mounted from `TableCanvas` and loaded only on a table page; blocks render the Svelte `BlockCard`. A tile is drawn like its source (`src/lib/table-post-source.ts`): a note, reply, like or repost fetches its post from the prerendered `<post>/source.json` and draws it with the post pages' own `NoteCard`/`SavedSocialPost` inside `SocialBlock` (a Bluesky or Mastodon post taken out of a page is drawn from the block); Are.na blocks are `ArenaBlock`, squares as Are.na draws them. Rows and thumbnails stay plain `BlockCard`s. Tables are stored in the `PUBLISHING_STATE` bucket (`tables/`); only the signed-in owner edits, and `?owner=demo` off production keeps tables in the browser. The tldraw licence key (`src/lib/tldraw-license.ts`) covers `*.caseyagollan.com` only; workers.dev previews and the branch Storybook use a second key from the Workers Builds variable `PUBLIC_TLDRAW_PREVIEW_LICENSE_KEY`, set on Previews only (`previews_base_config` of both Workers) and never committed. Without it, or once it expires, the canvas hides after five seconds there.
- Voice notes on tables (owner-only; `docs/tables/voice-notes.md`): the toolbar's microphone (`tables/VoiceControl`, Storybook `Tables/VoiceControl` and `Tables/TableCanvas` "Voice note") switches on a `VoiceNotes` session (`src/lib/voice-session.svelte.ts`) that writes what is heard into a text block as the words arrive, closes it at a pause and starts the next below. The rules are pure and tested in `src/lib/voice-notes.ts` (`tests/voice-notes.test.ts`): reading a transcriber's messages (`sttEvents`), a block as it is spoken (`hear`), joining and trimming rich text, and the model's question and answer (`refinePrompt`, `parseRefine`, which keeps the words as heard when an answer is no longer the passage). Listening (`src/lib/voice-source.ts`) tries the Worker first: the browser sends the microphone as 16-bit PCM over a WebSocket to `/api/tables/voice/listen`, which `worker.mjs` answers before SvelteKit with the Workers AI model's own socket (`voiceListen` in `src/lib/server/voice.ts`; Deepgram Flux, `@cf/deepgram/flux`, whose end of turn is the pause; `VOICE_MODEL` names another, such as nova-3 for other languages), for the signed-in owner on the site's own origin only. Where that socket doesn't open (a local run, the demo) the browser's own `SpeechRecognition` listens and pauses are timed. No audio is kept. The session's two choices are kept in `localStorage`: "Correct the text" and "Lay out and connect" each send a finished block to `POST /api/tables/voice` (owner and CSRF, previews included), one small completion through the chat's provider registry (`refineSpeech`: `VOICE_TEXT_MODEL`, else the chat's model, else any provider with a key), which answers the corrected words and the id of the block it follows. The canvas side is `tables/canvas/textBlocks.ts`: `voiceCanvas` (`TableApi.voice`) writes and rewrites blocks, and `settle` either draws a block up under the one before it or, arranging, ties it with `connect` to the block it follows and sets the tied blocks out with `arrange` as a tree. The same file gives every text block two outline habits (`installTextBlocks`, editable tables only): one dropped on another becomes part of it (`mergeTextBlocks`, arrows carried over, the target outlined while it is hovered), and Enter divides one at the caret (`splitTextBlock`; Shift+Enter is a new line, and lists keep Enter). `Permissions-Policy` allows the microphone to the site itself for this (`_headers` and `security-headers.ts`).
- Tags from a table (`src/lib/tag-edits.ts`, `src/lib/tag-edits.svelte.ts`, `src/lib/server/tags.ts`, `/api/tags`, owner-only): a block that stands for a post, a Raindrop bookmark or a Readwise item (Reader document, highlight, highlighted book) shows its tags along the bottom of its card (`TableBlock`), and the toolbar's Tags button opens `TagDock` (`TagEditor`, then `TagReview`; Storybook `Tags/*`) for the selection, or for every such block with nothing selected. A block finds its item by `tagRef`: a post by its address, the others by the `ref` their block keeps (`raindrop:<id>`, `readwise:document|highlight|book:<id>`; a Raindrop block from before refs is found by its link). Edits are staged in the browser (`localStorage`), never written as they are made; the review lists them by destination and saves on a press. Posts are saved as one commit to the content repository (`commitPostTags` in `src/lib/server/publishing/post-tags.ts`: `createCommitOnBranch` through `writeMany`, all files or none, refused if the branch moved): each post's `category` changes through the Micropub document functions, `updated` is set, and delivery is queued as after any Micropub update. It is not a Micropub extension. Raindrop takes a bookmark's whole tag list (`PUT /raindrop/<id>`), Reader takes whole lists fifty documents to a request (`/api/v3/bulk_update/`, 20 requests a minute, so reads are rationed and the rest come a minute later), and highlights and books add and remove one tag at a time (v2). Only `caseyagollan.com` writes: previews and `?owner=demo` rehearse (`dryRun`), saying what the commit would read and what each item's tags would become. The chat's `table_tag` reads tags and stages changes for ids, the selection or a frame (`tagOp` on the table page); it never saves.
- `src/lib/arena.ts`, `utils/arena.ts`, `src/lib/server/arena.ts`: Casey's Are.na (user `casey-gollan`, v3 API). The build puts Casey's own channels and blocks that anyone can see (public and closed) in the search index as type `arena`, at their Are.na addresses, so they show in site search, ⌘K and the tables Add menu; group channels and other people's items are dropped. It needs no token (guest limit 30 requests a minute; a profile is about ten pages); a failed fetch fails the build, like the wiki. Private blocks never go in the index: `/api/arena?q=` searches them for the signed-in owner only, using the Worker secret `ARENA_PAT`, with a ten-minute copy at `arena/private.json` in `PUBLISHING_STATE`. The owner's ⌘K ("Private on Are.na") and tables Add menu use it; tables are public, so a private block added to one becomes visible. Raindrop.io bookmarks work the same way, owner-only and never indexed: `/api/raindrop?q=` (`$lib/server/raindrop.ts`, Worker secret `RAINDROP_TOKEN`) searches Raindrop live, and the tables Add menu shows a Raindrop filter only to the signed-in owner (`withOwnerSources` in `src/lib/table-sources.ts`).
- Webmentions: the site keeps its own copy. The cron (`worker.mjs`) runs `syncWebmentions` (`src/lib/server/webmentions.ts`), which reads webmention.io's domain listing after `since_id` with the Worker secret `WEBMENTION_IO_TOKEN` and stores each post's mentions under `webmentions/` in `PUBLISHING_STATE`. Post pages and feed count chips read `/api/webmentions` (`Webmentions` → `WebmentionList`, `WebmentionCounts`), which falls back to webmention.io live until a bucket has been synced once (previews). The signed-in owner can hide one mention or everything from one person (`webmentions/moderation.json`); visitors never receive hidden ones. `?owner=demo` off production tries moderation without saving. Replies, favorites and reposts are also read straight from each post's own Mastodon and Bluesky copies (`src/lib/server/backfeed.ts`): the prerendered `/backfeed.json` lists posts with Casey's syndication URLs, the cron (at :05, :15, …) refreshes a few overdue posts per run (new posts every 10 minutes, old ones weekly) into `webmentions/backfeed/`, and `readMentions` merges them with Webmentions via `combineResponses`, dropping Bridgy's copies but keeping their ids so moderation carries over. Native mentions have `network`, a hashed `id` (`nativeId`, above 2^50) and `parent` for nested replies (`threadReplies`). Before the bucket has been read once (previews), post pages read them live.
- Responding: post pages end with `RespondBar` (Reply, Like, Repost), each a `Popover` holding `RespondPanel`. Logic is in `src/lib/respond.ts`: the post's first Bluesky and Mastodon copies come from `syndication` (`postCopies`). Bluesky links to the copy (or a compose intent), Mastodon asks for the visitor's server once (kept in `localStorage`) and opens `authorize_interaction` there, and "From your website" sends a Webmention to webmention.io from the browser (it allows CORS; without JavaScript the form posts there directly). Each button is wrapped in `<indie-action>` for indie-config. Responses come back through backfeed and Webmentions.
- `/chat` (experimental, owner-only for now): AI chat threads. While `CHAT_OWNER_ONLY` (`src/lib/chat.ts`) is true, `hooks.server.ts` 404s `/chat/*`, `worker.mjs` refuses thread sockets, the table overlay is left out, and the nav and ⌘K palette list Chat only for the owner (`ownerOnly` in `site-sections.ts`); set it false to open chat to visitors as described below. Each table has a thread (`tableThreadId`); its overlay can be minimized, floating or docked, and Casey's open table page carries out the assistant's `table_*` edits (`TableApi.perform`, `src/lib/table-agent.ts`); layouts are computed from measured shape bounds in `src/lib/table-layout.ts` (grid, masonry columns, tidy, overlap checks) and `src/lib/table-arrange.ts` (`arrange`: one deterministic call that sets out a whole table, some items or a frame's inside as `auto`, a tree, mind map, radial, layered flow via dagre, force-directed network via d3-force, named clusters in frames, or a tight pack, using the arrows tied to items as the graph, with frames as single boxes at the level above; research and trade-offs in `docs/tables/layout-research.md`), and every change reports leftover overlaps and arrows run through cards they don't join. The assistant has one tool per intent rather than per operation (`src/lib/server/chat/tools.ts`, whose header says why): `table_add` puts any mix of notes, text cards, links and search results on the table and sets them out in one call (the canvas op `add_notes` makes several notes in one change), `table_pull` (pictures and quotes out of blocks already there, by id, title words or Casey's selection: Casey's page reads each block's page with `pagePieces`, as the Add menu does, `pickPieces` in `src/lib/table-pieces.ts` keeps the first pictures and the most quotable passages, and they are set in the nearest open space beside their block (`freeSpot` in `table-layout.ts`, so nothing already there moves) with an arrow from the block to each; an are.na address is never read as a page, which is an app's empty shell with placeholder words: a channel gives its blocks' pictures and text through the API, a block its own picture and text plus the pieces of the page it links to), `table_arrange` fixes a layout in one call (every `arrange` mode, plus tidy and align; `inside` a frame by id or name; ids given are set out in that order), `table_move`, `table_connect` (arrows with tldraw arrow bindings to both items), `table_group` (a named frame, or a plain group), `table_edit` (words, colours, removing, renaming the table), `table_draw` (pen strokes, `around` loops that follow their item via `meta.around`), `table_select`, and `table_new`, which makes a draft table and opens it in Casey's browser. `table_add` is offered with no table open too (`needsTable` in `tools.ts` is what hides the rest) and then makes the table itself (`table`), so a first ask fills a table in one call; its `frames` adds several named frames in one call, set out in rows. Table changes run one at a time (`inTurn`) even when the model sends them together, so nothing lands on anything else. `table_edit` takes a `url` per edit to change where a block leads (`relink` op, resolved on the table page like `add_links`, then `set_blocks` on the canvas, keeping place, size and id). A reply the provider cut off at `maxTokens` (`stopReason: 'length'`, usually mid tool call) is carried on once through `onYield` (`CUT_OFF_NOTE`, `CUT_OFF_RETRIES`) instead of ending as a blank answer. Casey's selection on the canvas goes with every message (`chat:say`'s `selection`, from `TableState.selection` through `offerTable`): `sayPrefix` in `src/lib/chat.ts` tells the model the selected ids and titles, `["selected"]` stands for them wherever a table tool takes ids (`pick` in `tools.ts`; `table_read` with ids returns just those items in full), and `ChatSelection` shows it above the composer and on the sent message. Every change answers with the ids and boxes of what it touched, so the model doesn't re-read the table. `my_saves` (Casey's runs only, like the Micropub tools) reads Casey's Are.na, Raindrop and Readwise in full through `src/lib/server/saves.ts`: a source's channels, collections, or shelves and tags; everything one holds, 40 at a time; what matches some words; one item whole. It uses the Worker secrets `ARENA_PAT`, `RAINDROP_TOKEN` and `READWISE_ACCESS_TOKEN`, so private items come back marked `private`, and nothing it reads is cached anywhere public. A `table_add` item `{source, in}` puts a whole channel, collection, shelf or book's highlights on the table in one call (`add_blocks`, then a frame named after it, the frames side by side below what is there), leaving out what the table already holds. `table_look` has Casey's page draw the table with tldraw's `editor.toImage`, number each item and outline overlaps in red, and hands the picture to the model. `view_image` lets the model see any public picture (shrunk with the `IMAGES` binding); the model must take images (`input: ['text', 'image']` in `provider.ts`, true of glm-flash). Each thread is a Cloudflare Agents SDK agent (`ChatThread`, one SQLite Durable Object per thread, `src/lib/server/chat/agent.ts`) reached at `/agents/chat-thread/<id>` over WebSocket; `worker.mjs` routes it, refuses plain HTTP, and passes the viewer in a header it sets itself (`withViewer`). Anyone reads; signed-in visitors write. Visitors sign in with their website (IndieAuth client, `/chat/client.json`), Mastodon (per-instance app, token revoked after reading the profile) or Bluesky (atproto OAuth, `atproto` scope, `/chat/bluesky-client.json`, reusing `bluesky-oauth.ts`); sessions are under `chat/sessions/` in `PUBLISHING_STATE` (`src/lib/server/chat/identity.ts`, `login.ts`). Casey is recognized only by the passkey session. Pi Durable runs the assistant (`PiHarness` from `agents/harness/pi`, `@earendil-works/pi-*` pinned to the minor `agents` supports; never roll back across a Pi minor): transcript, retries, compaction, and resuming after eviction. People's messages are `chat.say` entries carrying the author and a server-set `owner` flag; `projection.ts` folds Pi's entries and `pi.live` into chat messages and diffs them for the socket. Tools and the system prompt are a Pi extension (`tools.ts`). Models come from a registry of providers (`src/lib/chat-models.ts`: inference.coop's OpenAI-compatible gateway, Anthropic's Messages API, Cerebras), each a pi-ai provider built in `provider.ts` and offered only where its Worker secret is set (`INFERENCE_COOP_API_KEY`, `ANTHROPIC_API_KEY`, `CEREBRAS_API_KEY`); a new provider is an entry there and a secret. New threads answer with `CHAT_MODEL` (default `glm-flash-green`). Casey picks another per chat from the composer's Model menu (`chat/ChatModelMenu`, the `ChoiceMenu` primitive with `text`, headings and detail lines): the browser sends `chat:model`, the thread keeps the key in its `model` meta, tells Pi's session (`session.setModel`, before the next answer) and sends Casey's browsers `chat:models`; with one provider there is no menu. The registry's prices feed the budget. The request hook in `tools.ts` speaks each provider's dialect: `reasoning_effort` for OpenAI-style providers; for Claude, adaptive thinking with `output_config.effort` (its larger models refuse `thinking: disabled`), and on a run's last round `tool_choice: none` with the tools kept. Claude's prompt caching is pi-ai's (breakpoints on the tools, the system prompt and the newest message) and holds because requests only ever grow: changing prompt sections go in as system messages after the history (`supportsMidConvoSystemMessages`), and the hook adds no message to a Claude request that isn't in the transcript. `model.ts` streams only the thread-naming call, always on inference.coop. Branch previews answer only because that secret is also in the Worker's Previews Base secrets (see the `previews` comment in `wrangler.jsonc`); without it a preview's chat stays silent. Each answer's cost is charged to the visitors it answered, per UTC month, at `chat/spend/` (`budget.ts`, var `CHAT_MONTHLY_BUDGET`, default $3; Casey is not capped). Needs the `enable_weak_ref` flag. Tools: `search_site` reads `/pagefind/agent-index.json`, which the search build writes beside Pagefind, and both searches it and lists it by date (`findDocuments` in `site-search.ts`: `days`, `since`, `until`, `type`, `tag`; Casey's own posts first, a count of each kind, each result's text); `fetch_page` uses defuddle (`fetch-page.ts`), reads the asker's own page when given no URL, and hands over long pages 8,000 characters at a time; the Micropub tools are offered and run only in a Pi run whose every input came from Casey's passkey session (hooks in `tools.ts`). Creating and updating go through the MCP bridge (`micropub-mcp.ts`, also served at `/micropub/mcp` for IndieAuth tokens); the chat's own `micropub_list_posts` and `micropub_get_post` ask Micropub directly and return a line per post, or one post's source, since the bridge's full sources overflow the model's context. The prompt carries today's date and the site's sections. Every request sets `reasoning_effort` (var `CHAT_REASONING_EFFORT`, default `low`): unset, the gateway's GLM thinks for thousands of tokens a step. A run's last allowed round is sent without tools, so it ends in an answer instead of "too many steps". `utils/chat-eval/` replays real questions against the real prompt and tools (`bun utils/chat-eval/run.ts`; the site read live, Micropub from `content/`, the table an in-memory stand-in): run it before and after changing a tool or the prompt. Thread summaries for the index live at `chat/threads/`. UI: `src/lib/components/chat/` (Storybook `Chat/*`), live client `src/lib/chat-client.svelte.ts`; streaming Markdown is closed with `remend`. A reply shows its steps where they happened: each `ChatToolUse` carries `at` (the length of the reply's text before it), `messageParts` in `src/lib/chat.ts` cuts the text there, and `ChatMessage` draws `ChatText` and `ChatSteps` in turn. `ChatSteps` is a line summing the steps up (`stepsSummary`, or the step under way while it runs) that opens to `ChatTool` rows, each opening to its picture, links, Request (`requestOf` in `projection.ts`) and Response (`JsonView`); both levels are the `Disclosure` primitive (ui-sdk Collapsible, closed panels are not in the page). Results of `micropub_*` and `my_saves` and the words of a post never go in a step's details (`isPrivateTool`). The full-page chat is a chat app's shell: `ChatLayout` (the list of chats down the left, `ChatSidebar`, grouped by day, with New chat and Search) gives the page the window's height beneath the trail and navigation, and each page puts its conversation and composer in a `ChatPane`, which scrolls by itself. ⌘K on a chat page lists chats and, for Casey only, searches them by title and by what was said: `ChatLayout` adds a `search` to its page commands (`PageCommands.search` in `src/lib/page-commands.svelte.ts`, which `SitePalette` calls as Casey types), answered by `/api/chat?search=` from `searchThreads` (`src/lib/server/chat/threads.ts`, ranking in `src/lib/chat-search.ts`). Each thread writes its words to `chat/search/<id>.json` in `PUBLISHING_STATE` beside its summary; a thread from before that is read from its Durable Object once. ## UI work: component-first, atomic design

Every UI change goes through the design system. Do not style a route or page directly.

1. **Find the component first.** Before touching markup or CSS, look for the existing component in `src/lib/components/` and in Storybook (`bun run storybook`, port 6006). Change that component, or extend it with a prop or variant, rather than adding a one-off style at the call site.
2. **Build on ui-sdk.** Interactive components wrap `@ui-sdk/svelte` (Menu, Popover, Button, SegmentedControl, Checkbox, Switch, Field/Input/Textarea, Toolbar, Avatar, Dialog, Command, Pagination) in `src/lib/components/ui/`. Before using ui-sdk, follow the `ui-sdk` skill (`.agents/skills/ui-sdk`) and read `node_modules/@ui-sdk/svelte/docs/llms.txt`, then only the component pages you need; for a component ui-sdk doesn't ship, search `docs/core.md` by heading and read `docs/rendering.md`. Never write `role="menu"`, `"dialog"`, `"toolbar"`, `"switch"` and the like by hand. Style parts through `data-slot` and state attributes (`data-open`, `data-checked`, `data-highlighted`); popups open in the top layer, so they need no z-index. Navigation stays plain links.
   **Prefer the web platform.** For any HTML, CSS or client-side script change, follow the `modern-web-guidance` skill (`.agents/skills/modern-web-guidance`): search it for the pattern first (`npx -y modern-web-guidance@latest search "<pattern>"`), and use a built-in feature with the fallback its guide names before writing custom script or adding a dependency.
   **Browser support:** features that are Baseline newly available (in current Chrome, Edge, Firefox and Safari) may be used without a script fallback or polyfill, as long as older browsers get a plainer result that still works. Features missing from any current major browser still need the fallback their guide names.
3. **Build up by atomic level.** Compose each level only from the levels below it:
   - **Atoms** (`src/lib/components/ui/`, Storybook `Primitives/*`): `Button`, `Icon`, `Chip`, `ToggleChip`, `Count`, `Avatar`, `TextField`, `Checkbox`, `Switch`, `Heading`. Tokens from `src/app.css` only; no layout or data knowledge.
   - **Molecules** (`ui/` and feature folders): small groups of atoms with one job, such as `SegmentedPill`, `SelectMenu`, `Popover`, `CommandPalette`, `CheckboxGroup`, `Pagination`, `PostMeta`, `PostTitle`.
   - **Organisms** (`posts/`, `composer/`, `editor/`, top-level `components/`, Storybook `Posts/*`, `Composer/*`, `Site/*`): self-contained sections such as `PostCard`, `PostFeed`, `Nav`, `Search`, `SitePalette` (⌘K; `/` opens `Search`), `ComposerBar`.
   - **Templates** (`Page`, `PageHeader`, `Section`, `PostsLayout`): page structure with slots, no route data.
   - **Pages** (`src/routes/**/+page.svelte`): load data and arrange templates and organisms. Routes hold no reusable markup and no `<style>` beyond one-off layout glue.
4. **Update Storybook in the same change.** Every new or changed component needs a story covering its new props, variants, and states (empty, loading, error, long content, mobile where relevant). Put the story next to the component (`Name.stories.ts` or `Name.stories.svelte`) under the matching Storybook group. If a token changes, update `Foundations/Tokens`.
5. **Promote, don't duplicate.** If a second place needs the same pattern, extract it into a component at the right level and replace both usages.
6. **Verify.** Run `bun run build-storybook` (or check `bun run storybook`) alongside tests and the production build, and look at the changed stories and the routes that use them.

## Editing and verification

- Inspect the working tree and preserve unrelated in-progress edits.
- Keep credentials out of source, logs, and commits. Local environment files are ignored.
- Preserve local dates, metadata, media, permalink behavior, and GitHub fallback behavior when changing post parsing.
- Do not cache mutable development content or fallback network responses across requests.
- Do not restore deleted archives, starter apps, generated output, Conductor workspaces, or browser screenshots to the repository.
- When editing Svelte, use `svelte-autofixer` if available; otherwise validate with the installed Svelte compiler and project checks.
- Verify deployed behavior directly before claiming a production fix; a build or upload alone is insufficient.
